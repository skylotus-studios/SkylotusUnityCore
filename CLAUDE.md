# CLAUDE.md

Guidance for Claude (or any agent) working in this repository. This is a Unity
6000.3.8f1, URP 2D project (`com.unity.render-pipelines.universal` 17.3.0), using
LitMotion for tweening and Input System 1.18 (no legacy input). It is the base template
Skylotus Studios clones into every new commercial project — code quality and API
stability here have a wider blast radius than a normal gameplay repo.

Read `CORE_FIXES.md` before touching anything under `Assets/Scripts/Core/Runtime/` or
`Assets/Scripts/Editor/` — it documents known defects, an active multi-agent fix plan
organized into work packages (WPs) and waves, and the file-ownership rules that plan
depends on. If you were dispatched as part of that plan, your WP's *Files* list is a hard
boundary: do not edit a file outside it. If you believe you need to, stop and report
rather than reaching across.

## Architecture rules (do not violate)

1. **Systems never reference each other directly.** `AudioManager` does not hold a
   reference to `UIManager`; `DialogueSystem` does not call into `NotificationSystem`
   directly. All cross-system communication goes through:
   - **`EventBus`** (`Assets/Scripts/Core/Runtime/Events/EventBus.cs`) — type-safe
     publish/subscribe for "something happened" notifications. Prefer struct event types
     (`IGameEvent`) to keep publish allocation-free. Immediate dispatch via `Publish`,
     deferred/queued dispatch via `Enqueue` + `ProcessQueue`.
   - **`ServiceLocator`** (`Assets/Scripts/Core/Runtime/ServiceLocator/ServiceLocator.cs`)
     — how one system obtains a reference to another when it genuinely needs to call a
     method on it (not just react to a notification). Register at bootstrap, resolve
     with `ServiceLocator.Get<T>()` or `TryGet<T>()` anywhere else.

   A new system should not add a `[SerializeField] private OtherSystem _other;` or a
   `FindObjectOfType<OtherSystem>()` to talk to another core system. If you find yourself
   wanting that, either publish/subscribe an event or register/resolve through the
   locator instead.

2. **Every public member gets an XML doc comment.** Every public type, method, property,
   and field in this codebase is documented — see any file under
   `Assets/Scripts/Core/Runtime/` for the expected density (a `<summary>`, and
   `<param>`/`<returns>`/`<typeparam>` where applicable). This is enforced by review, not
   by the compiler (no asmdef here sets `<GenerateDocumentationFile>`), so it is easy to
   silently skip — don't. `.editorconfig` documents this as policy.

3. **`.unity` / `.prefab` / `.mixer` / `.asset` files are never hand-authored as YAML.**
   These are generated by the Editor, driven headlessly through `-executeMethod` targets
   in `SkylotusCI` and run via `Tools\unity-verify.ps1 -Mode method`. If a task calls for
   a new or changed prefab, scene, mixer, or ScriptableObject asset, write (or extend) a
   generator method that builds it through the Unity API
   (`PrefabUtility.SaveAsPrefabAsset`, `EditorSceneManager.OpenScene`/`SaveScene`,
   `AssetDatabase.CreateAsset`, etc.) — do not open the `.prefab`/`.unity` text file and
   edit fields by hand. Text-editing that YAML is how a well-meaning change silently
   corrupts a `fileID` reference or a serialized GUID in a way that only shows up as a
   null reference at runtime.

4. **`SkylotusCI` is a partial class — never edit `SkylotusCI.cs` itself.** The base file
   (`Assets/Scripts/Editor/SkylotusCI.cs`) owns the shared helpers (`Succeed`, `Fail`,
   `SetObjectReference`, `RequireReference`, `RequireComponent<T>`) and a couple of
   foundational entry points (`CompileCheck`, `ValidateAssemblyReferences`,
   `GenerateCoreSystemsPrefab`). Everything added after that lives in its own
   `Assets/Scripts/Editor/SkylotusCI.<Area>.cs` (e.g. `SkylotusCI.Audio.cs`,
   `SkylotusCI.Project.cs`, `SkylotusCI.Build.cs`) as
   `public static partial class SkylotusCI`. This exists so parallel work packages adding
   `-executeMethod` targets don't all serialize behind edits to one file. Every entry
   point must be `public static void` with no parameters, must not assume a graphics
   device unless the caller passes `-Graphics`, and must call `Succeed`/`Fail` (or throw)
   so the process exits with a meaningful code under `-batchmode`.

5. **No `Resources.Load` calls.** This is an explicit rule from `CORE_FIXES.md` (see
   WP-16 — `Assets/Resources/` is already a known scaling problem: everything under it is
   force-included in every build and cannot be patched post-ship). Don't add new
   `Resources.Load` / `Resources.LoadAsync` call sites even though the existing core
   systems prefab and localization files currently live under `Assets/Resources/`.

## Verifying changes

The Editor GUI must be **closed** — Unity locks a project folder to one process, and a
batchmode call against a project the GUI has open fails immediately with exit code 1
(`unity-verify.ps1` detects this by process and exits 2 with a clear message instead of
letting it read as a compile failure).

```
cd C:\dev\SkylotusUnityCore
Tools\unity-verify.ps1 -Mode compile
```

is the minimum bar for "done" on any code change. It runs
`Unity.exe -batchmode -nographics -quit` and exits non-zero if anything failed to
compile. The script holds a named system mutex, so it is safe to run it freely even while
other agents are working — concurrent invocations queue instead of colliding on the
Unity project lock.

For an `-executeMethod` generator (asset generation, project-settings stamping):

```
Tools\unity-verify.ps1 -Mode method -Method Skylotus.Editor.SkylotusCI.<Method>
```

Add `-Graphics` if the method touches the render pipeline (instantiates a renderer,
builds UI, etc.) — the wrapper passes `-nographics` by default. For test runs, `-Mode
tests -TestPlatform EditMode|PlayMode`; for a full wave-boundary gate, `-Mode all`
(compile, then EditMode, then PlayMode).

CI (`.github/workflows/`) exercises the same underlying Unity flags through GameCI's
actions so local and CI verification cannot drift in what they consider "passing" — see
that workflow's comments for the exact correspondence, and note it is untested by this
agent, since GitHub Actions cannot be executed locally.

## Style

See `.editorconfig` for the mechanical rules (4-space indent, Allman braces, `_camelCase`
private/serialized fields, block-scoped namespaces — **not** file-scoped, i.e. always
`namespace Skylotus { ... }`, never `namespace Skylotus;`). When in doubt, match the
nearest existing file under `Assets/Scripts/Core/Runtime/` rather than a general C#
convention — this codebase has an established, consistent style that predates any
tooling default.

## Where things live

```
Assets/Scripts/Core/Runtime/    Core systems (EventBus, ServiceLocator, AudioManager,
                                 SaveSystem, LocalizationSystem, GameStateMachine,
                                 TimeManager, InputManager, UIManager, DialogueSystem,
                                 NotificationSystem, DebugConsole, ObjectPool, ...)
Assets/Scripts/Editor/          Editor-only tooling, including SkylotusCI's partials.
Assets/Scripts/MainMenu/        Main-menu screens and Settings tabs (view layer; should
                                 not own logic that belongs in a core system service).
Assets/Resources/Prefabs/       The generated core systems prefab and other
                                 Resources-loaded prefabs (see rule 5 above).
Assets/Scenes/                  BootScene (entry point), MainMenu, Gameplay.
Tools/unity-verify.ps1          Headless verification harness (see "Verifying changes").
CORE_FIXES.md                   The active fix/hardening plan — read it first.
```
