# Skylotus Core — Pre-Fork Fix Plan

Everything below must land **before** this repo is cloned as the base for a real project.

Findings are from a full read of every script in `Assets/Scripts/`, both gameplay scenes,
`Packages/manifest.json`, `ProjectSettings/`, and `Skylotus.Core.Runtime.asmdef`
(Unity 6000.3.8f1, URP 2D, LitMotion, Input System 1.18).

---

## How to use this document

Each **work package (WP)** below is self-contained and sized for one subagent in `opusplan` mode.
Give the agent the WP's *Problem*, *Required change*, and *Acceptance criteria* verbatim, plus its
*Files* list as the ownership boundary.

**Rules for dispatch:**

1. **Respect the waves.** Packages in the same wave touch disjoint file sets and can run fully in
   parallel. Packages in later waves depend on earlier ones — either for a file lock or an API.
2. **A WP owns its files exclusively.** No agent edits a file outside its *Files* list. If an agent
   believes it needs to, it should stop and report rather than reach across the boundary.
3. **Agents drive Unity through the CLI, not the GUI.** WP-0 provides `Tools/unity-verify.ps1`,
   which runs the Editor headlessly for compile checks, `-executeMethod` asset generation, and test
   runs. Any WP marked **[gen]** must produce its `.prefab` / `.mixer` / `.asset` via a generator
   method in `SkylotusCI` invoked through that script — **never** by hand-authoring YAML.
4. **Scene and asset YAML is off-limits.** Same rule, stated for emphasis: `.unity`, `.prefab`,
   `.mixer`, and `.asset` files are generated by the Editor via `-executeMethod`, never edited as
   text. WP-1 is the only package that modifies a scene, and it does so through
   `EditorSceneManager.OpenScene` / `SaveScene` in a generator method.
5. **The Editor must be closed while agents work.** Unity locks a project folder to one process.
   With the Editor GUI open, every batchmode call fails with exit code 1 immediately after
   `Successfully changed project path` — which reads like a compile failure but is not.
   `unity-verify.ps1` detects a **GUI** Editor by process and exits **2** with a clear message.
6. **Verification is serialized; run it freely.** `unity-verify.ps1` holds a named system mutex, so
   concurrent agents queue instead of colliding on the project lock — a second caller prints
   `waiting for another verify run to finish` and proceeds when the first is done. Agents should
   self-verify rather than deferring to a wave-boundary check. Always go through the script; a raw
   `Unity.exe -batchmode` call bypasses the mutex and will fail against a running sibling.
7. **`SkylotusCI` is a partial class.** Any package adding an `-executeMethod` target creates its
   own `Assets/Scripts/Editor/SkylotusCI.<Area>.cs` and **does not edit `SkylotusCI.cs`**, which
   three packages would otherwise contend for. The shared helpers (`Succeed`, `Fail`,
   `SetObjectReference`, `RequireReference`, `RequireComponent<T>`) are available to every partial.

**Definition of done for every WP:** `Tools\unity-verify.ps1 -Mode compile` exits 0; XML doc
comments match the surrounding style (this codebase documents every public member); no new
`Resources.Load` calls; no behavior change outside the stated scope.

**Files:** `Tools/unity-verify.ps1`, `Assets/Scripts/Editor/SkylotusCI.cs`

One correction made during verification: `ValidateAssemblyReferences` originally scanned every
asmdef in the project and reported **27** unresolved references — 25 of them false positives from
Unity's own packages, which routinely reference assemblies that are not installed (optional
integrations gated by `versionDefines`, platform modules, test-only deps). It is now scoped to
`Assets/` and reports exactly the two real ones. Any future check that walks the asset database
should apply the same scoping.

### Problem

Every acceptance criterion in this document is unverifiable by an agent that cannot run Unity, and
four packages need `.prefab` / `.mixer` / `.asset` files that must not be hand-authored as YAML.

The environment already has what's needed: Unity 6000.3.8f1 at
`C:\Program Files\Unity\Hub\Editor\6000.3.8f1\Editor\Unity.exe`, with a working license
(batchmode connects to `LicenseClient-Nandan` successfully).

### Required change

`Tools/unity-verify.ps1` wraps four invocations:

| Mode | Unity flags | Use |
|------|-------------|-----|
| `compile` | `-batchmode -nographics -quit` | Non-zero exit = scripts failed to compile |
| `method` | `... -executeMethod <Type.Method>` | Asset generation, project-settings stamping |
| `tests` | `-batchmode -nographics -runTests -testPlatform <p> -testResults <xml>` | WP-12; parses NUnit XML |
| `all` | compile → EditMode → PlayMode | Wave-boundary gate |

`Assets/Scripts/Editor/SkylotusCI.cs` is the home for every `-executeMethod` entry point. It ships
with `CompileCheck()` (plumbing smoke test) and `ValidateAssemblyReferences()` (catches the WP-10
phantom-asmdef class of bug automatically). Asset-generating WPs add their generator here.

Two flags that matter: `-runTests` must **not** be combined with `-quit`, and asset generation that
touches the render pipeline needs `-Graphics` (the wrapper passes `-nographics` by default).

### Acceptance criteria

- [x] With the Editor closed, `Tools\unity-verify.ps1 -Mode compile` exits 0.
- [x] `-Method Skylotus.Editor.SkylotusCI.CompileCheck` exits 0 and logs the assembly counts.
- [x] `-Method Skylotus.Editor.SkylotusCI.ValidateAssemblyReferences` **fails** on the current tree,
      reporting exactly `Unity.Addressables` and `Unity.ResourceManager` as unresolved (this is
      WP-10's bug — the harness proving it can see it). **It must pass once WP-10 lands**, which is
      the regression test for that package.
- [x] With the Editor open, any mode exits **2** with the lock message, not a misleading compile
      error.

### Two premises in this document were wrong

Both were found by the implementing agents and confirmed:

1. **WP-7.** This document claimed `Spawn` parenting to `null` "places it in the active scene", so a
   scene load destroys the object and leaves a tombstone. False. `Bootstrapper.cs:189-191` does
   `SetParent(null)` then `DontDestroyOnLoad(root)`, and `ObjectPool._root` sits under that root — so
   a null-parent spawn becomes a root of the **DontDestroyOnLoad scene** and is never destroyed. The
   real defect was the opposite: pooled objects silently **persist** across scenes. WP-7 added
   `MoveGameObjectToScene` so the documented behaviour is now true. **If persistence was actually
   wanted, revert that and reword the criterion instead.**
2. **WP-11.** This document claimed `applicationIdentifier` was empty. It was a nested map holding
   `Standalone: com.DefaultCompany.2D-URP`, with stale differently-cased Android/iOS ids. Likewise
   `managedStrippingLevel: {}` meant "platform default" (`Minimal`), not "unset". The grep that
   produced both claims only saw the map keys.

### Open decisions for a human

- ~~**LICENSE**~~ **RESOLVED (2026-08-31).** Decision: **source-available, all rights reserved** —
  public so the code can be read and learned from, with use, copying, modification and
  redistribution withheld. `LICENSE` now states this, notes that a GitHub fork is not a grant of
  those rights, and carries a third-party section. This matches what the default already was; the
  file makes it deliberate rather than an apparent oversight.
- **A purchased asset pack is sitting in that public repo.** `Assets/Animated Loading Icons/`
  (spritesheet, prefabs, animations, vendor documentation PDF) carries **no licence file**. Unity
  Asset Store's standard EULA generally forbids redistributing pack contents in a form third parties
  can extract — a public repo does exactly that. This is independent of whichever licence is chosen
  for Skylotus's own code, and should be checked against wherever the pack came from. The other
  vendored items are clearer: `UnityEditorDarkMode.dll` is MIT (its README carries the text) and
  TextMeshPro ships with Unity.
- **IL2CPP is set but not buildable on this machine.** WP-11 set the Standalone backend to IL2CPP,
  but the editor install has only `*_mono` variations — the *Windows Build Support (IL2CPP)* module
  is not installed. WP-11's "a clean clone can produce a Windows standalone build" criterion cannot
  be met until it is. Escape hatch: `SKYLOTUS_SCRIPTING_BACKEND=Mono2x`.
- **`.editorconfig` line endings.** WP-13 sampled only `Assets/Scripts/Core/Runtime/` (pure LF) and
  wrote `end_of_line = lf` for all `*.cs`. The repo is mixed — `Assets/Scripts/MainMenu/*.cs` are
  CRLF. With `core.autocrlf=true`, an editor honouring `.editorconfig` will rewrite those files
  wholesale on first save. Either normalize them or relax the rule.
- **`SkylotusProject.json`** does not exist in the repo. Decide whether it is gitignored per-clone or
  committed per-project.
- **Running the harness mutates tracked project settings.** Every batchmode run opens the project,
  and Unity 6 migrates settings assets on open. Observed after wave 1:
  `ProjectSettings/TimeManager.asset` rewrote `Fixed Timestep: 0.02` into the `serializedVersion: 2`
  rational form (same value), and `ProjectSettings/QualitySettings.asset` went `serializedVersion:
  4 → 5` adding `meshLodThreshold`. Both are benign and will recur on any Editor open.
  **One change in that batch is not benign:** the **Low** quality level's `vSyncCount` flipped
  `0 → 1`. No package asked for it and no `PlayerPrefs` keys exist, so it came from the migration's
  re-defaulting. Decide whether Low should ship with VSync on; if not, revert that line before
  committing — and note it will come back on the next Editor open unless the asset is pinned.
- **`com.unity.localization`.** WP-15 recommends *not* adopting now, but migrating the moment a
  second shipped language is committed to — there are currently zero `LocalizedText` components in
  any scene (verified) and three call sites, so this is the cheapest migration point the project will
  ever have. RTL forces the decision: neither this system nor bare TMP can render it.

### A third premise was wrong, and a fourth writer existed

- **WP-4 found a fourth `Time.timeScale` writer** this document never listed: `DebugConsole`'s

### A latent runtime bug, found by writing tests — no WP owns it

`CustomCursor.UpdateMouseCursor` (`CustomCursor.cs:146`) falls back to legacy
`UnityEngine.Input.mousePosition` when `Mouse.current == null`. This project runs
`activeInputHandler: 1` — **Input System only** — where touching legacy `Input` throws. So on any
mouseless device the cursor code throws *every frame*.

It surfaced because it broke **19 of 45** PlayMode tests the moment one loaded `Gameplay.unity`
(which carries `CursorCanvas`). WP-12 routed around it by loading `BootScene` instead, and did not
fix it — correctly, since the file was outside its boundary. **This needs its own work package.** It
is not a test-only problem.

### `GC.GetAllocatedBytesForCurrentThread()` is useless in Unity

WP-12's first zero-allocation test used it and **passed even with a deliberate `new object()` inside
the measured window** — the API returns 0 unconditionally on this runtime. That is the exact
"green suite that asserts nothing" failure the negative-control practice exists to catch, and it
caught itself. Use the test framework's `Is.Not.AllocatingGCMemory()` (GC.Alloc profiler recorder)
instead. Note this does **not** invalidate WP-8's earlier measurement, which ran on CoreCLR in a
standalone harness where the API works — but a Unity-side test must not use it.

### Brightness needed more than a volume override

WP-3 found that **all three scenes ship with `m_RenderPostProcessing: 0`** — every camera in the
project. Without URP's post-processing pass, any volume-stack brightness is invisible, so this
document's WP-3 spec was incomplete. `DefaultVolumeProfile.asset` already carried an active
`ColorAdjustments` with `postExposure` overridden, so no asset change was needed at all. The
controller now forces `renderPostProcessing` on at runtime while brightness ≠ default and restores
the cameras it changed. **Ticking the box in the three scenes is the cleaner fix** and would let that
workaround be deleted.

WP-3 also created a **new assembly**, `Skylotus.Core.Rendering`, because `Skylotus.Core.Runtime.asmdef`
has zero URP references and belongs to WP-10. If one assembly is preferred, the alternative is two
added references on that asmdef plus moving the file up a folder.

### Six negative controls were run

WP-4, WP-15 and WP-12 all broke a passing assertion, confirmed the failure, and reverted. WP-12 did
this for six tests including WP-7's scene-load survival and WP-1's loading screen — the two criteria
whose original authors could only reason about them. That practice is what turned this suite from
"green" into "green and meaningful", and it is worth making mandatory.

### One flaky test — a real CI risk

`EventBusTests.EnqueueThenProcessQueue_AllocatesNothingPerEvent` is **not deterministic**. WP-10
observed 2 failures in 7 runs; both were on the **first EditMode run after a script recompile**, and
both passed on an immediate re-run with no source change. WP-10 confirmed it is not caused by its own
work by stashing everything and reproducing against the clean tree at `7108cd6`.

Four further runs here all passed — but **that is not a refutation**: those runs had no source
changes between them, so the recompile trigger never occurred. **CI compiles fresh on every run**, so
this is more likely to fire there than locally.

Likely mechanism: `Is.Not.AllocatingGCMemory()` is backed by a **process-wide** GC.Alloc profiler
recorder, so Editor-side allocations inside the sampled window get attributed to the measured
delegate. Do **not** "fix" it by widening the tolerance — that silently guts a WP-8 acceptance
criterion, and this is the same assertion that already caught itself being vacuous once. Diagnosing
it properly is its own work package.

`SettingsService.Flush()`, bypassing the dirty flag. Both are documented rather than fixed.

Also still stale: `ServiceLocator.Get<T>()`'s exception message says "Did you forget to register it
in SkylotusBootstrapper?" — a type that has not existed since before wave 1.

# Part A — Defects (blocking)

## WP-1 — Bootstrapped systems can never be configured

**Severity:** Blocking · **Wave:** 1 · **[gen]** (needs WP-0)

**Status: DONE** (2026-08-31), verified independently of the implementing agent: `-Mode compile`
exit 0, `ValidateCoreSystemsPrefab` exit 0, `BootScene.unity` diff is exactly one line (the prefab
reference), init order confirmed by reading the source. Prefab is
`Assets/Resources/Prefabs/SkylotusCoreSystems.prefab`, guid `f0502fd7d14a3e44d863e61960b65065`.

Three criteria are **not** CLI-verifiable and are carried to WP-12 as PlayMode tests: the loading
screen actually fading and driving the bar 0→1; all 14 systems registering in order with no
double-registration; an inspector value observably changing behaviour. Nothing in the project
currently exercises the loading-screen path — `Bootstrapper.Start()` loads the first scene with
`showLoadingScreen: false`.

**Files:** `Assets/Scripts/Core/Runtime/Bootstrap/Bootstrapper.cs`,
`Assets/Scripts/Core/Runtime/SceneManagement/SceneManager.cs`,
`Assets/Scripts/Core/Runtime/UI/UIManager.cs`, `Assets/Scenes/BootScene.unity`,
new prefab under `Assets/Resources/Prefabs/`

**Conflicts with:** WP-2, WP-4, WP-5, WP-6, WP-10 — all deferred to later waves.

### Problem

`Bootstrapper.InitializeSystems()` builds every system with `new GameObject()` + `AddComponent`
(`Bootstrapper.cs:125-188`, via `CreateChild` at `Bootstrapper.cs:202`). Components created this way
get **default values for every `[SerializeField]`, permanently and unreachably.**

The visible consequence: `SceneManager._loadingScreen` and `_progressBar` (`SceneManager.cs:20,23`)
are always `null`, so `LoadScene(name, showLoadingScreen: true)` is a silent no-op. The README
advertises loading screens with progress bars as a headline feature; they have never worked.
`UIManager._screenContainer` / `_modalContainer` (`UIManager.cs:69,72`) are null for the same
reason, as are the tuning knobs on `AudioManager`, `NotificationSystem`, and `UIManager`.

### Required change

Replace code-constructed systems with a single **`[Skylotus Core]` prefab** holding every system
component pre-wired, instantiated by the bootstrapper at boot. Concretely:

- Add a `[SerializeField] private GameObject _coreSystemsPrefab;` to `Bootstrapper`, instantiate it,
  `DontDestroyOnLoad` it, then `GetComponentInChildren<T>()` each system and register it with
  `ServiceLocator`. Preserve the existing initialization **order** (logger → save → localization →
  audio → pool → scene → state → time → input → UI → dialogue → notification → console).
- The prefab carries a loading-screen `Canvas` (CanvasGroup + Slider) wired into `SceneManager`, and
  screen/modal container transforms wired into `UIManager`.
- Keep the reflection-based `InputActionAsset` injection at `Bootstrapper.cs:152-166` **only** if the
  prefab cannot carry the reference; prefer wiring it on the prefab and deleting the reflection.
- Fall back to the current code-construction path if `_coreSystemsPrefab` is null, so an un-migrated
  boot scene still runs.

Build the prefab in `SkylotusCI.GenerateCoreSystemsPrefab()` (WP-0), driven by:

```
Tools\unity-verify.ps1 -Mode method -Graphics `
  -Method Skylotus.Editor.SkylotusCI.GenerateCoreSystemsPrefab
```

The same method opens `BootScene.unity` via `EditorSceneManager.OpenScene`, assigns the prefab to
the `Bootstrapper`, and saves. `-Graphics` is required — the loading-screen Canvas needs a render
context. Do not hand-edit the scene or prefab YAML.

### Acceptance criteria

- The generator runs clean from the CLI and produces both the prefab and the updated scene.
- `LoadScene("X", showLoadingScreen: true)` fades in an actual overlay, drives the progress bar 0→1,
  and fades out.
- Every system's inspector values are editable on the prefab and observably take effect at runtime.
- Entering play from `BootScene` registers all 14 systems, in the original order, with no
  double-registration warnings from `ServiceLocator.Register` (`ServiceLocator.cs:40`).

## WP-2 — Saved settings are never applied at startup

**Severity:** Blocking · **Wave:** 2 (needs WP-1, WP-9)

**Files:** new `Assets/Scripts/Core/Runtime/Settings/SettingsService.cs`,
`Assets/Scripts/MainMenu/Settings/SettingsAudioTab.cs`,
`Assets/Scripts/MainMenu/Settings/SettingsVideoTab.cs`,
`Assets/Scripts/MainMenu/Settings/SettingsGameplayTab.cs`,
`Assets/Scripts/Core/Runtime/Bootstrap/Bootstrapper.cs`

### Problem

Every persisted setting is read **only inside the settings UI's `OnEnable`**. Audio volumes load at
`SettingsAudioTab.cs:46-54`; resolution, fullscreen, quality, VSync and brightness load in
`SettingsVideoTab.OnEnable` (`SettingsVideoTab.cs:64-73`).

So a player who sets master volume to 20%, quits, and relaunches gets **100% volume** — until they
happen to open Settings → Audio, at which point it silently jumps to 20% mid-session. Same for
quality level and VSync. There is no boot-time "apply saved settings" step anywhere in the project.

### Required change

Introduce a `SettingsService` that **owns** every settings key and both directions of the flow:

- Single source of truth for the PlayerPrefs key names, currently duplicated as private consts
  across the three tab classes (`SettingsVideoTab.cs:38-42`, `SettingsAudioTab.cs:43`).
- `ApplyAll()` — reads every saved value and pushes it into `AudioManager`, `QualitySettings`,
  `Screen`, and the brightness hook (WP-3), with typed defaults when a key is absent.
- Registered and `ApplyAll()`-ed by `Bootstrapper` **before the first scene loads**, i.e. before the
  `LoadScene` call in `Bootstrapper.Start()`.
- Rewrite the three tab classes to read/write through `SettingsService` instead of touching
  `PlayerPrefs` directly. Tabs become pure view code.
- Drop the `PlayerPrefs.Save()` call from every individual setter (it is a synchronous disk flush on
  every slider tick); flush on screen close and on `OnApplicationPause` / `OnApplicationQuit`.

### Acceptance criteria

- Change master volume → quit → relaunch → volume is correct **before** any settings screen opens.
- Same for quality level, VSync, fullscreen mode, resolution, and every gameplay-tab setting.

## WP-7 — `ObjectPool` does not survive scene loads

**Severity:** High · **Wave:** 1

**Files:** `Assets/Scripts/Core/Runtime/Pooling/ObjectPool.cs`

### Problem

Three separate issues in one file:

1. **Scene-load leak.** `Spawn` parents the object to `parent`, which is `null` by default
   (`ObjectPool.cs:147`), placing it in the active scene. A single-mode `LoadScene` destroys it, but
   the (now-destroyed) reference stays in `pool.Active` forever. Over a few scene transitions the
   pool fills with tombstones, `GetActiveCount` lies, and `DespawnAll` iterates corpses.
2. **`MaxSize` is not a cap.** The expand check tests `pool.Active.Count < pool.MaxSize`
   (`ObjectPool.cs:131`), ignoring `Available.Count`. Total instantiated objects can exceed
   `maxSize` by the size of the available queue.
3. **`Despawn` is O(pools).** It linear-scans every pool's `Active` HashSet to find the owner
   (`ObjectPool.cs:189`). With many pools and a high despawn rate this is measurable.

Related: the "recycle the oldest" branch pulls an arbitrary element out of a `HashSet` — there is no
ordering, so "oldest" is a lie. It happens to function only because `Available` is known-empty at
that point.

### Required change

- Track instance→pool ownership in a `Dictionary<int, Pool>` keyed by instance ID so `Despawn` is
  O(1) and `ReturnToPool` needs no search.
- Subscribe to `UnityEngine.SceneManagement.SceneManager.sceneUnloaded` (or implement
  `IPoolable`-aware cleanup) to purge destroyed instances from `Active` and `Available`.
- Cap on `Active.Count + Available.Count` against `MaxSize`.
- Replace the `HashSet` "oldest" recycle with a real ordered structure, or rename the behavior
  honestly and document it.
- Null-guard every dequeue (`Available` can hold destroyed objects after a scene change).

### Acceptance criteria

- Spawn 50 pooled objects → load a new scene → `GetActiveCount` reports 0 and no null-reference
  exceptions occur on the next `Spawn`.
- `CreatePool(p, 10, maxSize: 20)` never produces more than 20 total instances under sustained spawn
  pressure.
- `Despawn` performs no iteration over `_pools`.

## WP-8 — `EventBus` deferred path uses reflection; subscriptions leak

**Severity:** Medium-High · **Wave:** 1

**Files:** `Assets/Scripts/Core/Runtime/Events/EventBus.cs`

### Problem

1. **`DynamicInvoke` per queued event.** `ProcessQueue` dispatches with
   `entry.Handler.DynamicInvoke(evt)` (`EventBus.cs:172`) — reflection-based invocation, roughly two
   orders of magnitude slower than a direct call, running every frame via `EventQueueProcessor`.
   `Enqueue` also boxes the struct into `object` (`EventBus.cs:149`). The README's headline claim for
   this system is "zero GC (struct events)"; the deferred path allocates on every enqueue.
2. **No lifecycle safety.** The bus is `static` and survives scene loads, but subscribers are
   MonoBehaviours that don't. One missed `Unsubscribe` in `OnDestroy` and the handler fires against a
   destroyed object forever — and because `Publish` wraps handlers in try/catch
   (`EventBus.cs:126-133`), this degrades into permanent silent log spam rather than a loud failure.
   Only two call sites subscribe today and both unsubscribe correctly; the risk is entirely in what
   gets built on top.

### Required change

- Replace the boxed queue with per-type typed queues (`Dictionary<Type, Queue<T>>` via a generic
  holder class, or a `List<IEventQueue>` of typed queues) so `ProcessQueue` casts to `Action<T>` and
  invokes directly, with no boxing and no reflection.
- Add a lifecycle helper — an extension like `this.SubscribeWhileAlive<T>(handler)` on
  `MonoBehaviour`, or a small `EventBusBinder` that auto-unsubscribes on destroy — and document it as
  the default path for new code.
- Have `Publish` log the handler's target type on exception so a leaked subscriber is diagnosable.

### Acceptance criteria

- `Enqueue` → `ProcessQueue` allocates zero bytes per event (verify with the Profiler or a
  `GC.GetAllocatedBytesForCurrentThread` test).
- No `DynamicInvoke` remains in the file.
- Destroying a subscriber that used the lifecycle helper stops delivery with no manual unsubscribe.

## WP-14 — `SaveSystem` hardening

**Severity:** Medium-High · **Wave:** 1

**Files:** `Assets/Scripts/Core/Runtime/Save/SaveSystem.cs`

### Problem

The structure is sound (slot files, versioned wrapper, IV-prefixed AES, path-traversal
sanitization). Four production gaps:

1. **Non-atomic writes.** `File.WriteAllText` (`SaveSystem.cs:100`) — power loss or a crash mid-write
   leaves a truncated, unparseable save. There is no backup, no `.bak` rotation, no
   temp-file-and-move.
2. **No migration path.** A version mismatch only logs a warning (`SaveSystem.cs:139`) and then
   deserializes the old payload anyway, producing silently wrong data.
3. **`JsonUtility` limits.** No `Dictionary`, no polymorphism, no `Nullable<T>`, no top-level arrays.
   Save-data models will hit this quickly, and the constraint is undocumented.
4. **Synchronous I/O** on the main thread — a large save hitches the frame.

Also worth stating plainly in the docs: `_saveEncryptionKey` is a serialized field on the scene
object (`Bootstrapper.cs:40`), so it ships inside the build and is trivially recoverable. That is
fine as anti-tamper friction; it must not be described as security.

### Required change

Write to `slot.tmp` → `File.Replace` onto the real file, keeping the previous version as `slot.bak`;
fall back to `.bak` when the primary fails to parse. Add a registerable migration hook
(`RegisterMigration(int from, int to, Func<string,string>)`) invoked on version mismatch, and refuse
to load — loudly — when no migration path exists. Add `SaveAsync` / `LoadAsync`. Document the
`JsonUtility` constraints and the encryption threat model in the class summary.

### Acceptance criteria

- A save interrupted mid-write leaves either the previous save or the new one intact — never a
  corrupt file.
- Loading a version-2 file with only a 1→2 migration registered succeeds; with none registered it
  fails loudly rather than returning garbage.
- Round-trip tests pass encrypted and plaintext (see WP-12).
